# tw-glass — Engineering Review

## Executive summary

The package is in good shape for an early (0.0.5) release: the generated CSS is content-correct, the Tailwind v4 wiring resolves cleanly via the `style` export condition, and the README utilities table matches the generated output with no drift. There are no broken-render or perf defects in the shipped CSS path for the browsers it actually serves (Chromium/Safari). The single most important thing to fix is the **shared custom-property design**: `glass-strength-*` and `glass-chromatic-*` both write `--tw-glass-filter`, and `glass` overloads Tailwind's own `--tw-backdrop-blur` slot — so the two headline axes can't combine and `glass` silently fights stock `backdrop-blur-*` utilities, all with no error. The rest is mostly accuracy (README overclaims Firefox), accessibility hardening (no `@supports` / forced-colors fallbacks), and build-process hygiene (the generator is orphaned with no wired script or CI guard).

Note on a pre-established fact: running the generator today produces output that is **value-identical** to the committed `src/index.css`; the only difference is whitespace/line-wrapping (generator emits one long line, committed file is formatter-wrapped). So "build workflow" findings below are about *process risk and noisy diffs*, not current content drift.

## Correctness & browser compat

**[HIGH] `glass-strength-*` and `glass-chromatic-*` cannot be combined (shared filter slot)** — Every `@utility glass-strength-N` and every `glass-chromatic-N` assigns the *same* property `--tw-glass-filter` (`src/index.css:84-132`). They're equal-specificity single-class utilities, so `class="glass glass-strength-40 glass-chromatic-20"` resolves `--tw-glass-filter` to exactly one value — the loser is silently dropped, with the winner decided by Tailwind's emitted utility order (not something the user can fix by reordering classes). The two marquee axes are effectively mutually exclusive, and the failure is invisible. Recommend either documenting it honestly (chromatic supersedes strength), or — better — making chromatic an independent axis (e.g. a `--tw-glass-chromatic-scale`) so refraction + chromatic compose. This pairs naturally with the single-map refactor below. *(`src/index.css`, `scripts/generate.mjs:188-205`)*

**[MEDIUM] `glass` clobbers stock Tailwind `backdrop-blur-*` via the shared `--tw-backdrop-blur` slot** — `glass` injects the displacement filter into Tailwind's own blur slot: `--tw-backdrop-blur: var(--tw-glass-filter) blur(var(--tw-glass-blur));` (`src/index.css:51`). Tailwind's `backdrop-blur-*` writes that same property, so `class="glass backdrop-blur-md"` drops one wholesale — either the refraction `url()` vanishes or the user's blur is ignored. The README *invites* this collision ("layer on... backdrop utilities for stronger effects," `README.md:31`). Mitigating factor: the package ships its own `glass-blur-{n}` modifier (`src/index.css:136-138`), which is the intended in-vocabulary way to change blur, so reaching for stock `backdrop-blur-*` is a secondary path. Fix: compose the displacement through a private `backdrop-filter` declaration in `@layer components` ahead of Tailwind's chain so a user's `backdrop-blur-md` only replaces the blur term; at minimum drop the README invitation and document the incompatibility.

**[MEDIUM] README claims Firefox support, but Firefox can't reference an SVG `url(#f)` filter from `backdrop-filter`** — `README.md:49`: "Works in all browsers that support `backdrop-filter` with SVG filter references (Chrome, Edge, Safari, Firefox)." The core effect depends on `backdrop-filter` resolving `var(--tw-glass-filter)` = `url("data:...#f")` (`src/index.css:50`, composed at `:64-68`). Firefox supports the `backdrop-filter` *property* but not SVG-filter *references* in it — that path is Chromium-specific. In Firefox only the chained `blur()/brightness()/saturate()` functions degrade through; the refraction (the plugin's whole purpose) does not render. Confidence high. Fix the wording to: full refraction in Chromium (Chrome/Edge) and Safari; Firefox falls back to no displacement. *(Verify the Safari claim in real Safari — see next finding.)*

**[MEDIUM] No `@supports` fallback; `glass-surface` degrades to an ~8% white tint where the filter no-ops** — There is no `@supports` guard anywhere in the file (verified by grep) and the `.glass` rule applies `backdrop-filter` unconditionally (`src/index.css:56-80`). `glass-surface` backs the panel with only `rgb(255 255 255 / var(--glass-bg-opacity))`, default 8% (`:44`, `:75`). On engines that ignore `url()`-referenced backdrop filters (notably **WebKit/Safari — verify this in real Safari**, since it determines how widely this bites), a `glass glass-surface` panel collapses to a near-transparent tint over which text can fall below WCAG contrast. Note the impact is scoped to `glass-surface`; plain `glass` sets no background, so a no-op there is visual-fidelity loss, not a contrast failure. The `prefers-reduced-transparency` angle is weak (niche media-query support). Fix: gate the displacement behind `@supports (backdrop-filter: url('#x'))` with a more opaque tint in the unsupported branch.

**[MEDIUM] Displacement map rounds at `rx=4` but `glass-surface` paints a 16px corner** — `generate.mjs:14` hardcodes `REF_RADIUS = 4`, and `buildFeImage` emits the displacement source's rounded rect at that radius, while the same stylesheet ships `glass-surface { border-radius: 1rem; }` (16px). The refraction follows a near-square 4px corner inside a 16px-rounded card, so edge distortion visibly leaks past or stops short of the painted corner. Reproduced throughout the project's own demos (`apps/docs/app/tw-glass/(home)/page.tsx` pairs `glass-strength-20 rounded-3xl`, `glass-strength-30 rounded-2xl`, etc.). It undermines the exact card use case the package recommends. Fix: parameterize the corner (a `glass-radius-*` family regenerating a per-radius map), or at minimum set `glass-surface`'s radius to match the map's ~4px tuning and document the mismatch. *(Critic-added; not independently adversarially verified.)*

**[MEDIUM] `glass` silently creates a new stacking context + containing block** — A non-`none` `backdrop-filter` on `glass` forms a new stacking context **and** acts as a containing block for `position: fixed`/`absolute` descendants (same rule as `filter`/`transform`). A repo-wide grep for `isolation`/`stacking`/`containing` found nothing, and the README doesn't warn about it. Any consumer placing a fixed modal/tooltip or absolutely-positioned child inside a `.glass` element will find it positioned relative to the glass box, not the viewport — a classic hard-to-debug regression. Fix: add a "Gotchas" section to the README documenting this known `backdrop-filter` side effect and the workaround (hoist overlays out of the glass subtree). *(Critic-added; not independently adversarially verified.)*

**[MEDIUM] No `forced-colors` / Windows High Contrast fallback** — Grep for `forced-colors` returns nothing. The effect relies entirely on translucency (white tints, faint border, `box-shadow`). In forced-colors mode browsers disable `backdrop-filter`, drop box-shadow, and force the palette, so glass-surface borders/fills collapse and card boundaries become invisible. This is a separate media feature from `prefers-reduced-transparency`. Fix: add `@media (forced-colors: active)` giving `glass-surface` a `border: 1px solid CanvasText` and solid `background-color: Canvas`. *(Critic-added; not independently adversarially verified.)*

**[LOW] `glass-text` is invisible when no background image is set/loaded** — `glass-text { color: transparent; background-clip: text; ... }` (`src/index.css:164-170`) provides no `background-image`/`background-color` and no `@supports` guard. With no background, during image load, or on a 404, glyphs render fully transparent while staying in the DOM. This is the inherent tradeoff of the `background-clip:text` technique on an opt-in, single-purpose utility (its documented job is to clip a user-supplied background), so real risk is the pre-load/404 window plus the missing `@supports` fallback. Fix: ship a default background and/or gate `color: transparent` behind `@supports ((-webkit-background-clip: text) or (background-clip: text))` with an opaque fallback. *(This subsumes the separate `@supports`-only finding; the missing feature query is the same fix, and modern engines have supported `-webkit-background-clip:text` for ~9 years, so the feature-query gap alone is near-empty in real browsers.)*

**[LOW] `--glass-bg-opacity` is `inherits: true` while sibling vars are `inherits: false`** — `@property --glass-bg-opacity { inherits: true; initial-value: 0.08; }` (`src/index.css:41-45`) vs `--tw-glass-blur/brightness/saturation` all `inherits: false` (`:23-39`). Because it inherits, applying `glass-bg-30` on an ancestor silently overrides the surface opacity of any nested `glass-surface` descendant meant to use the 0.08 default. Nested glass-surface is uncommon, but it's an undocumented footgun. Fix: set `inherits: false` to match the others (in both `generate.mjs:122` and the CSS), or document the deliberate inheritance.

**[NIT] README/comment recommend `background-attachment: fixed` for `glass-text`, broken on iOS Safari** — `README.md:26` and the comment at `src/index.css:153-162` suggest `background-attachment: fixed` for a parallax-window effect. iOS Safari renders this as `scroll` (no viewport-fixed parallax, possible mis-sizing). The package never sets it itself; it's opt-in guidance. Fix: a one-line caveat that the parallax effect is desktop-oriented and unreliable on iOS Safari.

## Tailwind v4 coupling

**[MEDIUM] `backdrop-filter` composition hard-codes Tailwind's 9 private `--tw-backdrop-*` variable names** — The `@layer components .glass` rule (`src/index.css:59-68`, generated from `generate.mjs:141-151`) reproduces Tailwind's internal composition verbatim: the exact ordered list of `var(--tw-backdrop-blur,) ... var(--tw-backdrop-sepia,)`. The generator comment (`generate.mjs:127-139`) admits it's "working around" Tailwind owning `backdrop-filter` and "mirrors what Tailwind generates." This is an **undocumented internal contract**: if a future v4.x reorders/renames/adds a backdrop primitive or changes stripping behavior, the glass effect breaks with no build error (the trailing-comma fallbacks resolve to empty). Aggravating: `peerDependencies` is `>=4.0.0-0` (open-ended), claiming support for every future v4 while depending on internals. It renders fine against current Tailwind, so this is latent. Fix: add a CI integration test that compiles against the pinned Tailwind and asserts `.glass` still emits a non-empty `backdrop-filter` referencing the filter `url()`; narrow the peer upper bound; document the reliance in the README.

**[LOW] Functional utilities reject arbitrary-value syntax (`glass-blur-[7]`)** — `glass-blur-*`/saturation/brightness/bg use `--value(number)` only (`src/index.css:136-150`), which matches the bare numeric scale but not the `[...]` branch (which needs `--value([length])`/`--value([number])`). So `glass-blur-[7]` matches nothing and emits no class — a silent no-op for a power user. All documented named values work; arbitrary support was never advertised. Fix: broaden to `--value([length], number)` (apply `* 1px` only on the bare-number branch), or document that only the named scale is accepted.

**[LOW] The docs tuner hand-duplicates the private `--tw-backdrop-*` composition string** — The tuner's "Compiled CSS" output hard-codes the same 9-variable Tailwind-internal string by hand (`tuner/page.tsx:177,180`, both prefixed and unprefixed), separate from `generate.mjs:141-151` and `src/index.css:59-68`. That's a **third copy** of the brittle contract that must move in lockstep, and the tuner copy is user-facing (it feeds the "Copy" button), so a drifted composition hands users broken copy-paste CSS. Fix: export the composition string (and an `@layer components` helper) from `filter-builder.mjs` and consume it in both `generate.mjs` and the tuner — collapsing three copies to one source.

## Build & regenerate workflow

**[MEDIUM] Generator is orphaned — empty `"scripts": {}`, no regenerate/verify guard** — `package.json` has `"scripts": {}`; `src/index.css` is generated by `scripts/generate.mjs` (`writeFileSync(..., css)`) yet `main`/`exports`/`style` all point at that file and `files` ships only `src` + README (scripts/ unpublished). There is no `generate`/`build`/`prepack`/`prepublishOnly` and no CI step asserting committed == regenerated. Today there's **no content drift** (the established fact), so this is a process/maintainability gap, not a current bug: if someone edits `filter-builder.mjs` and forgets to regenerate, the shipped CSS silently diverges and nothing fails. Compounding it, a naive `node scripts/generate.mjs` re-collapses the `@layer components` block to one line (generator output isn't piped through the repo formatter; `.oxfmtrc.json` exists at the root), producing a noisy whitespace-only diff. Fix (single highest-leverage change here): add `"generate": "node scripts/generate.mjs && <repo formatter> src/index.css"` so output is byte-identical to committed, plus a `"generate:check"` that regenerates to temp, formats, and `git diff --exit-code`s — wired into CI. Optionally `"prepack": "pnpm generate"`.

**[LOW] Zero tests; hand-written `.d.mts` can silently drift from the `.mjs`** — `filter-builder.d.mts` is hand-maintained beside the untyped `filter-builder.mjs`, with no `tsc`/test/typecheck step. Signatures match today, so this is latent. But the encoding logic is the package's correctness core (a one-character `.replace` error yields a silently non-rendering filter), and `buildChromaticFilter`'s optional `rRatio`/`gRatio` defaults are exercised only by the tuner (`generate.mjs` always calls `buildChromaticFilter(map, scale)`) — exactly the path most likely to drift unnoticed. The monorepo already has vitest infra (commit `3820dc415`). Fix: add a test asserting `toDataUri(buildStandardFilter(encodeSvgUrl(map), scale))` starts with `url("data:image/svg+xml,`, ends with `#f")`, contains no raw `<`/`>`/`#`, and that the double-encoded inner `#` round-trips; add a `typecheck` that wires the `.d.mts` into the monorepo typecheck.

**[LOW] Duplicated-but-divergent minify+encode logic in `encodeSvgUrl` vs `toDataUri`** — Both functions (`filter-builder.mjs:64`, `:163`) start with the byte-identical minify regex and a similar percent-encode chain, but diverge on quote handling (`encodeSvgUrl` does `"`→`%22`/`'`→`%27`; `toDataUri` does `"`→`'` first). The double-encoding contract is correct today, but its correctness depends on exact ordering (the `%`→`%25` pass must run before any step introducing new `%`). A well-meaning "unify these" cleanup would double- or mis-escape and silently break the data URI. Fix: extract a shared `minifySvg()` helper, add a comment in `toDataUri` explaining the intentional `%`-re-escape (the double-encoding contract), and lock it in with the round-trip test above.

**[LOW] Misleading JSDoc: `@param` says "Base64-encoded" but the value is URL-encoded** — `buildStandardFilter`'s JSDoc says `@param {string} mapBase64 - Base64-encoded...` (`filter-builder.mjs:103`), but the actual param is `mapUrlEncoded` and it's produced by `encodeSvgUrl` (percent-encoding). The `generate.mjs` header repeats "base64-encoded once" for the map. `buildChromaticFilter`'s JSDoc correctly says "URL-encoded," so the doc set is internally contradictory and could mislead a future maintainer into wiring up real base64. Fix: correct the `@param` to `mapUrlEncoded - URL-encoded...` and fix the `generate.mjs` header.

## API & bundle

**[LOW] 38KB headline overstates impact; realistic page ships ~1.1KB gzip** — Measured: raw `src/index.css` = 38,704 B, but gzip = ~2.4KB and brotli = 1,793 B (the SVG data URIs are highly redundant and compress hard). A realistic `glass` + `glass-strength-30` + `glass-chromatic-20` subset is ~8.9KB raw / ~1.1KB gzip. So this is **source/repo hygiene and tarball weight, not a consumer-bundle emergency** — don't frame it as one. Genuine costs: source readability, the full 38KB shipped in the tarball, and the pathological all-12-steps consumer (~2.4KB gzip).

**[LOW] Displacement map is inlined 13× identically; could be de-duplicated** — `generate.mjs:188-205` (plus the base `glass` default) embeds the full feImage map blob into every filter; `feImage(mapUrlEncoded)` builds a byte-identical map for all 13 — only `feDisplacementMap scale=` differs. Note: Tailwind `@utility` blocks are tree-shaken, so a typical consumer ships only the variants they use — this is **source-bloat + maintainability** (a map tweak regenerates 13 blobs), not a 13× per-consumer runtime cost. The "hold the map in one CSS var the SVG reads" idea is **not viable** — a `data:` URI's decoded SVG cannot read CSS custom properties, and `feDisplacementMap@scale` has no CSS-property form. Feasible path: stop double-inlining the map in both `glass` and a strength block, and collapse source duplication.

**[LOW] `glass-strength-*` reimplements a single scalar as 6 discrete blocks — but it can't become a `glass-blur-*`-style functional utility** — The 6 strength blocks (`src/index.css:84-106`) differ only in the SVG `scale=` attribute. Tempting to make it functional like blur, **but that's infeasible under the pure-CSS/no-JS architecture**: blur/saturation/brightness set CSS custom properties that `backdrop-filter` reads at cascade time, whereas the displacement scale lives in the `feDisplacementMap@scale` attribute baked inside a `data:` URI — unreachable by `var()`, and the in-DOM `url(#filter)` workaround would require injecting `<svg>` (breaking "no JS runtime"). A genuine but smaller win remains: reduce source duplication, or expose a functional `glass-strength-*` that maps to one of the pre-baked URIs. (Also note: a `/200` formula would silently shift `strength-5` from 0.03 to 0.025, since it's the one point not exactly `name/200`.)

**[LOW] `glass-surface` hardcodes white tints with no dark-mode token story** — Only opacity is tokenized (`--glass-bg-opacity`); the tint color (`255 255 255`) and inset-highlight alphas are literals (`src/index.css:74-80`). No `--tw-glass-tint`, no `glass-surface-dark`, no dark-mode README example. A low-opacity white sheen over dark is the *intended* glass material (and the monorepo's own dark-context demos use plain `glass-surface` without overrides), so this isn't a theme defect — it's a token-coverage gap: a consumer wanting a smoked/black or brand-colored tint must override `background`/`box-shadow` wholesale. Fix: expose `--tw-glass-tint: 255 255 255` used inside `rgb()`.

**[NIT] Two value models + a default that sits mid-scale** — Strength is a discrete ramp `5,10,20,30,40,50` with `DEFAULT_STRENGTH = "20"` (`generate.mjs:26-29`), while blur/saturation/brightness/bg are continuous functional utilities. The "users can't tell what bare `glass` gives vs `glass-strength-20`" concern is **already addressed** — the generator builds `glass` from `DEFAULT_STRENGTH`, so they're provably identical, and the README documents it. The residual nit is cosmetic: discrete-vs-continuous inconsistency across axes and a non-round default.

## Docs & demos

**[MEDIUM] GPU/compositing cost of many simultaneous glass elements is undocumented — the project's own stress-test renders 150 live backdrop-filters** — `stress-test/page.tsx` sets `COUNT = 150` and renders that many `.glass` divs, each a separate compositing layer running an SVG displacement pass. No `will-change`/`contain` guidance and no performance note in the README (its only browser note is Firefox). This is a runtime GPU cost distinct from the bundle-size finding. Dozens of simultaneous glass elements (a realistic dashboard/list) can cause large VRAM use, dropped frames on scroll, and battery drain on low-end GPUs, with no signal to adopters. Fix: document a performance budget in the README ("each `.glass` is a separate compositing layer; avoid more than a handful on scroll-heavy lists"). *(Critic-added; not independently adversarially verified.)*

**[MEDIUM] Tuner deep-imports raw `.mjs` across the package boundary** — `tuner/page.tsx:4-10` imports five builders via a 5-level relative climb into `tw-glass/scripts/` — neither in `exports` nor `files`, and tw-glass isn't in `next.config`'s `transpilePackages`. It works only because the relative path physically reaches the sibling file; refactoring `scripts/` would silently break the docs build with no contract signal. *(Correction to an earlier draft: importing `.mjs` does NOT skip the co-located `.d.mts` — TS resolves declaration files by basename, so the `.d.mts` is consulted. The `as string` casts exist because the hand-written `.d.mts` is incomplete/stubbed, not because types fail to flow.)* Impact is confined to an internal docs page. Fix: add a sub-path export (`"./filter-builder": { "types": "./scripts/filter-builder.d.mts", "default": "./scripts/filter-builder.mjs" }`) plus `scripts` to `files` and import by package name, or extract a shared internal builder module. *(This is the same root issue as the packaging finding below — fixing one fixes both.)*

**[MEDIUM] All ~19 tuner range sliders are unlabeled for assistive tech** — The reusable `Slider` (`tuner/page.tsx:702-736`) renders `<input type="range" ...>` with the visible label in a sibling `<span>` — no `<label htmlFor>`, `id`, or `aria-label`. Every Map/Filter/Appearance control flows through it, so all announce as a nameless "slider." This is inconsistent with the project's own correct pattern: stress-test's `SliderControl` wires `<label htmlFor>` + `id`, and the tuner's own checkbox is properly wrapped. Keyboard operability is fine; this is a screen-reader/voice-control gap on the flagship demo. Fix: add `id` + `<label htmlFor>` (mirror `SliderControl`) or `aria-label={label}`; also give `BlendSelect` (`:769-799`) `role="radiogroup"` + per-button `aria-pressed`/`role="radio"`.

**[LOW] Hero attaches an always-on global `mousemove` listener with no reduced-motion or visibility gate** — `glass-text-hero.tsx:61-69` adds a `window` `mousemove` listener for the page's lifetime, driving springs that mutate SVG `fePointLight` x/y on a `text-9xl` lighting filter. No `prefers-reduced-motion` check and no IntersectionObserver. *(The handler updates DOM attrs via refs and springs are rAF-batched, so per-event cost is modest — not "two springs of main-thread work" per move.)* The real costs: the lighting-filter recompute keeps running on every spring tick even after the hero scrolls off-screen, and motion-opt-out users still get cursor-chasing lighting. Fix: skip updates (or don't attach the listener) when `matchMedia('(prefers-reduced-motion: reduce)').matches`, and optionally gate on viewport intersection.

**[LOW] `glass-text` demos clip remote photos into text with no fallback color or contrast floor** — Demos set `backgroundImage` to a remote Unsplash URL with no fallback `color` (`stress-test-text/page.tsx:142-163`; `glass-text-hero.tsx:224-235`), so a CDN failure renders the heading invisible. `BG_VARIANTS` also clips low-contrast fills (`Solid #888`, `Dark #222`, `:374-380`) and the "Long Copy" section presents body-size glass paragraphs — a real low-vision legibility problem. Confined to docs/demo pages, and DOM text stays screen-readable. These demos model a copy-paste pattern, so fix: pair `background-clip:text` with a solid fallback `color`, ensure demo backgrounds clear WCAG contrast, and treat body-size glass text as decorative.

**[LOW] Duplicated scaffolding across stress-test pages + three divergent `unsplash()` helpers** — `useFps`/`FpsCounter`, `SliderControl`, `Section`/`TestCard`/`TableOfContents` are duplicated (mostly byte-identical) across `stress-test/page.tsx` and `stress-test-text/page.tsx`. There are three `unsplash` helpers, and the drift already happened: `(home)/pattern-picker.tsx:5` exports `q=90` while both stress-test files declare local copies at `q=80`. The exported `pattern-picker` helper is already reused by four other consumers — only the stress-test pages reinvent it. Fix: extract the shared components into a `tw-glass/_shared` module and reuse the single exported `unsplash` (parameterize quality if the difference is intentional).

**[NIT] Tuner bubbles keyed by array index, restarting animations when sliders change** — `tuner/page.tsx:636-638` uses `key={i}`; `computeBubbles` regenerates the array on every slider change and each bubble carries an inline negative-delay `animation` string, so React rewrites animation strings in place and the running animations snap. Cosmetic, demo-only. Fix: derive a stable `id` from the deterministic seed (bubbles are already index-seeded), or accept the index key as intentional.

1. **Fix or honestly document the two custom-property collisions.** This is the highest-leverage correctness work: (a) make `glass-chromatic-*` an independent axis from `glass-strength-*` (separate scalar, not a shared `--tw-glass-filter`), and (b) stop hijacking `--tw-backdrop-blur` so `glass` composes with stock `backdrop-blur-*`. If a code fix is out of scope short-term, at minimum remove the README:31 "layer on... backdrop utilities" invitation and document both incompatibilities loudly.
2. **Correct the README browser-support line.** Drop Firefox from the supported list for the refraction path; state Chromium + Safari, and **verify the displacement effect in real Safari** before finalizing the wording (this also determines how widely the no-`@supports`-fallback issue bites).
3. **Add an `@supports` / forced-colors fallback for `glass-surface`.** Gate the displacement behind `@supports (backdrop-filter: url('#x'))` with a more opaque tint, and add `@media (forced-colors: active)` with `CanvasText`/`Canvas`. Prevents low-contrast/invisible panels where the filter no-ops.
4. **Reconcile the corner radius.** Either set `glass-surface`'s `border-radius` to match the map's `REF_RADIUS=4` tuning, or parameterize the corner — the current 4px-vs-16px mismatch is visible on the package's own recommended card pattern.

5. **Wire the generator.** Add `"generate"` (generator + repo formatter so output is byte-identical to committed), a `"generate:check"` CI guard (`git diff --exit-code`), and optionally `"prepack"`. Closes the silent-drift loop and kills the noisy whitespace diff.
6. **Add a Tailwind-contract integration test + narrow `peerDependencies`.** Compile against pinned Tailwind, assert `.glass` emits a non-empty `backdrop-filter` referencing the filter `url()`; cap the peer upper bound to a tested version; document the reliance on Tailwind internals.
7. **Give the tuner a stable contract for the builders.** Add a sub-path export with types (or extract a shared module), removing the cross-boundary deep import. Also collapse the three copies of the `--tw-backdrop-*` composition string to one exported source.
8. **Add the round-trip encoding test + typecheck.** Lock in the double-encoding contract (vitest infra already exists) and wire the hand-written `.d.mts` into typecheck so it can't drift.
